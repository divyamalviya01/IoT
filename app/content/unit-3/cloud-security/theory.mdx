<Callout kind="definition" title="In one line">
Cloud security protects the data, accounts, services and device connections an IoT system keeps in the cloud. The provider secures the cloud itself; the customer must secure everything they put in it.
</Callout>

## Why the cloud is a high-value target

An IoT cloud holds every device's readings and can send commands to all of them. One stolen admin password or one wrongly shared storage folder can expose a whole fleet at once, far more than a single hacked device.

## The shared responsibility model

The <Term id="shared-responsibility">shared responsibility model</Term> splits the work. The provider always secures the physical data centres, the hardware and the services it runs for you. What the customer must secure depends on the service model (topic 3.1).

## Identity and access management (IAM)

<Term id="iam">IAM</Term> decides who and what can do which actions.

- **Least privilege:** each person, app and device gets only the permissions it needs. A temperature sensor may publish to its own topic, nothing else.
- **Multi-factor login** for every human account, especially administrators.
- **Roles instead of shared passwords:** apps and services get temporary credentials through roles, not keys pasted into code.
- **Separate duties:** no single account can both change security rules and delete logs.
- **Review and remove:** delete accounts and keys that are no longer used.

## Encryption and key management

- **In transit:** TLS for every connection: devices (MQTT on 8883), apps (HTTPS) and service-to-service traffic.
- **At rest:** databases, storage and backups are encrypted.
- **<Term id="key-management">Key management</Term>:** keys are created, stored, rotated and destroyed by a key management service (KMS). The most valuable keys live in a hardware security module (HSM). Data is usually encrypted with a data key, which is itself encrypted by a master key that never leaves the KMS.

## Device identity: every device proves who it is

Each device should have its **own** identity, never a password shared by all devices.

- **X.509 certificate and private key:** the device's identity card. The private key is best kept in a <Term id="secure-element">secure element</Term> or TPM chip, where it can be used but never read out.
- **<Term id="mutual-tls">Mutual TLS</Term>:** the server proves itself to the device with its certificate, and the device proves itself to the server with its own. AWS IoT Core, for example, uses X.509 client certificates over mutual TLS for device connections.
- **Provisioning:** certificates are loaded at the factory or issued automatically when a device first connects (for example Azure's Device Provisioning Service).
- **Revocation:** a stolen or retired device's certificate is cancelled, so it can no longer connect.

## Watch and respond

- Turn on **audit logs** for every account and service, and keep them where attackers cannot delete them.
- **Alert** on unusual events: a device connecting from a new country, thousands of failed logins, a key used at 3 a.m.
- Have an **incident plan**. In India, CERT-In's 2022 directions require many organisations to report cyber incidents within 6 hours.

<Callout kind="example" title="An open storage folder">
A start-up stores clips from its doorbell cameras in cloud storage. A developer makes one folder public "just for a test" and forgets it. Months later, anyone with the link can watch thousands of clips. The provider's data centre was perfectly secure; the configuration was the customer's job. Automatic configuration checks would have flagged the public folder on the first day.
</Callout>
