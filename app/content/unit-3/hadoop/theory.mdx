<Callout kind="definition" title="In one line">
Hadoop is an open-source Apache framework that stores huge files across many ordinary computers and processes them in parallel, right where the data is stored.
</Callout>

## Why Hadoop?

Years of IoT readings can fill terabytes. One computer cannot hold that much, and reading it from one disk would take days. Disks also fail: in a cluster of a thousand machines, some break every week.

<Term id="hadoop">Hadoop</Term> solves both problems:

- It splits files into large blocks and spreads **copies** of each block over many cheap machines, so a failed disk loses nothing.
- It sends the **program to the data**, so each machine processes the blocks it already holds, all at the same time.

Hadoop was created by Doug Cutting and Mike Cafarella around 2006, based on two Google papers (the Google File System, 2003, and MapReduce, 2004). It became a top-level Apache project in 2008, and is named after a toy elephant.

## HDFS: storing huge files

<Term id="hdfs">HDFS</Term> (Hadoop Distributed File System) has one master and many workers.

- **<Term id="namenode">NameNode</Term> (master):** keeps the index: which blocks make up each file and which machines hold them. It stores no file data.
- **<Term id="datanode">DataNodes</Term> (workers):** store the blocks and send the NameNode a **heartbeat every 3 seconds**.
- **Secondary NameNode:** despite its name, it is *not* a backup. It only merges the NameNode's change log into a fresh checkpoint. For real fail-over, clusters run a **Standby NameNode** (high availability).

**Blocks and copies**

- A file is cut into <Term id="hdfs-block">blocks</Term> of **128 MB** by default (64 MB in Hadoop 1). Only the last block may be smaller.
- Each block is stored **3 times** by default: the <Term id="replication-factor">replication factor</Term>.
- Copies are placed **rack-aware**: the first on the writer's node, the second on a node in a **different rack**, the third on another node in that **same remote rack**. A whole rack can lose power without losing data.

<Callout kind="remember" title="Worked example">
A 500 MB file with 128 MB blocks becomes 4 blocks: 128 + 128 + 128 + 116 MB. With replication factor 3 there are 12 block copies, using 1500 MB of disk.
</Callout>

**When a DataNode fails**, its heartbeats stop. After about 10 minutes without a heartbeat, the NameNode treats it as dead. It then makes new copies of every block that now has fewer than 3, from the surviving copies. Lab L23 and the Visualize tab show this. If **every** copy of a block is lost, that part of the file is gone, which is why a replication factor of 1 is risky.

HDFS is built for **write once, read many**: large files written once and read in big sequential sweeps, not small files edited often. Hadoop 3 adds **erasure coding**, which protects data with about 1.5 times the space instead of 3 times.

## MapReduce: processing in parallel

<Term id="mapreduce">MapReduce</Term> splits a job into steps that run on many machines at once. Example: find the average temperature of each sensor from log lines such as `S1,08:00,24.3`.

  caption="MapReduce: every mapper and reducer runs in parallel on a different machine."

1. **Map:** each mapper reads its split and emits a key–value pair per line, here (sensor, temperature).
2. **<Term id="shuffle">Shuffle and sort</Term>:** every pair travels to the reducer responsible for its key, so all S1 values meet at one reducer.
3. **Reduce:** each reducer combines its groups, here into an average.

A <Term id="combiner">combiner</Term> is a mini-reduce on each mapper. It sends (S1, sum, count) instead of every single reading, so far less data crosses the network in the shuffle.

## YARN: sharing the cluster

<Term id="yarn">YARN</Term> (Yet Another Resource Negotiator) decides which job gets which machines.

- **ResourceManager:** one per cluster; hands out resources.
- **NodeManager:** one per machine; runs and watches the tasks there.
- **ApplicationMaster:** one per job; asks for resources and tracks the job's tasks.

Because of YARN, other engines such as Spark can run on the same Hadoop cluster.

<Term id="spark">Apache Spark</Term> keeps data in memory between steps, so it is usually much faster than MapReduce, and it can also process streams.

<Callout kind="example" title="Finding power theft">
An electricity company stores five years of smart-meter readings in HDFS. Every night, a batch job compares the energy entering each feeder with the total of its meters. Feeders where too much energy goes missing are listed for inspection the next morning.
</Callout>

## Advantages and limitations

**Advantages**

- Runs on cheap, ordinary computers and grows by adding more.
- Survives disk, machine and even rack failures through replication.
- Moves the program to the data, avoiding huge transfers.
- Open source, with a large ecosystem.

**Limitations**

- MapReduce is batch-only and slow for real-time answers.
- Poor with very many small files (each one costs NameNode memory).
- Complex to set up and run.
- Three copies use three times the disk (erasure coding helps).
