HTTP is the web's request–response protocol: a client sends a request with a method such as GET or PUT to a URL, and the server sends back a response with a status code and data.

## What is HTTP?

HTTP (HyperText Transfer Protocol) is the protocol your browser uses to load web pages. It runs over TCP, on port 80, or port 443 for HTTPS, its encrypted form.

HTTP is also used by many IoT devices and almost every IoT cloud platform. A device can upload readings with HTTP, and apps read device data through HTTP APIs.

HTTP is **request–response**: the client always starts, and the server only answers. It is also **stateless**: each request is handled on its own, so it must carry everything the server needs.

A request has a **method**, a **path** (part of the URL), **headers** and sometimes a **body**. A response has a <Term id="status-code">status code</Term>, headers and usually a body.

## REST: designing IoT APIs

<Term id="rest">REST</Term> (Representational State Transfer) is a popular way to design HTTP APIs, described by Roy Fielding in 2000. Each thing is a **resource** with its own URL, and standard methods act on it.

For an IoT device, resources might be `/sensors/temperature`, `/actuators/led` and `/settings`. Data is usually sent as JSON.

## The cost of HTTP on small devices

HTTP/1.1 headers are plain text. A simple request can carry 100–300 bytes of headers to send a 4-byte reading. Opening a new TCP connection for each request adds a handshake too.

<Callout kind="remember">
For a small reading, HTTP's headers can be fifty times bigger than the data. MQTT and CoAP were designed to avoid exactly this. HTTP/2 shrinks headers by compressing them, but most small devices still use HTTP/1.1.
</Callout>

## Polling and webhooks

Because the client always starts, an app that wants updates must keep asking. This is <Term id="polling">polling</Term>. If it polls every 5 seconds but the value changes once an hour, almost every request is wasted.

A <Term id="webhook">webhook</Term> turns this around. The app registers a URL, and the server calls that URL only when something happens. Server-sent events and WebSockets also let servers push updates.

When you pay with UPI, the shop's payment app does not keep asking the bank whether money has arrived. The payment provider calls the shop's server (a webhook) the moment the payment succeeds, and the shop's speaker announces it.

## Advantages and limitations for IoT

**Advantages**

- Understood everywhere: every language, cloud and firewall supports it.
- Simple REST APIs that are easy to test with a browser or tools like curl.
- Works through firewalls and proxies that block other protocols.
- HTTPS gives strong, well-tested security.

**Limitations**

- Large text headers waste bandwidth and battery.
- Request–response only: no built-in way for a server to push updates.
- TCP connections and TLS handshakes are heavy for small devices.
- Polling for updates wastes requests and energy.
