<Callout kind="definition" title="In one line">
MQTT is a lightweight publish–subscribe messaging protocol: devices publish messages to named topics on a broker, and the broker forwards each message to every client subscribed to that topic.
</Callout>

## What is MQTT?

<Term id="mqtt">MQTT</Term> (Message Queuing Telemetry Transport) is the most widely used messaging protocol in IoT. It runs over TCP and keeps messages very small: the smallest MQTT message header is just 2 bytes.

Andy Stanford-Clark of IBM and Arlen Nipper created MQTT in 1999 to monitor oil pipelines over expensive satellite links. It became an OASIS open standard in 2014 (version 3.1.1), and MQTT 5.0 followed in 2019.

MQTT normally uses TCP port 1883, or port 8883 when encrypted with TLS.

## Publish–subscribe vs request–response

With HTTP, a client asks a server for data and waits for the answer. This is request–response.

MQTT works differently. Senders, called **publishers**, send messages without knowing who will receive them. Receivers, called **subscribers**, say which messages they want. A server in the middle, the <Term id="broker">broker</Term>, matches them up.

## The broker

The broker is the post office of MQTT. It accepts connections from clients, receives every published message and forwards a copy to each client whose subscription matches.

Because clients only talk to the broker, a sensor never needs to know how many apps are listening, and new apps can be added without touching the sensor.

## Topics and wildcards

Every MQTT message has a <Term id="topic">topic</Term>: a text label with levels separated by slashes, such as `home/livingroom/temperature`.

Subscribers can use <Term id="wildcard">wildcards</Term> to match many topics with one subscription:

- **`+` (single level):** matches exactly one level. `home/+/temperature` matches `home/kitchen/temperature` but not `home/kitchen/fridge/temperature`.
- **`#` (multi level):** matches all remaining levels, and must come last. `home/#` matches everything under `home`.

<CompareTable
  caption="Which topics does each subscription match?"

/>

<Callout kind="remember">
Topics are case-sensitive: `Home/temp` and `home/temp` are different topics. Topics starting with `$`, such as `$SYS/…`, are reserved for broker statistics and are not matched by a leading wildcard.
</Callout>

## Retained messages, Last Will and sessions

<CompareTable
  caption="Useful MQTT features"
  columns={["Feature", "What it does", "Example"]}
  rows={[
    ["Retained message", "The broker keeps the last message on a topic and sends it to every new subscriber straight away", "A new phone app instantly shows the last known temperature"],
    ["Last Will and Testament", "A message the client leaves with the broker, published if the client disconnects unexpectedly", "“sensor-7 offline” is published when its battery dies"],
    ["Keep-alive", "The client sends a small PINGREQ if it has been quiet, so the broker knows it is still there", "Every 60 seconds"],
    ["Clean session", "The broker forgets the client's subscriptions when it disconnects", "A dashboard that only wants live data"],
    ["Persistent session", "The broker remembers subscriptions and stores QoS 1 and 2 messages while the client is offline", "A phone that loses signal in a lift"],
  ]}
/>

A <Term id="retained-message">retained message</Term> is the "last known value" of a topic. The <Term id="last-will">Last Will</Term> is set when the client connects. <Term id="keep-alive">Keep-alive</Term> messages let the broker notice a silent, dead client.

## Publish–subscribe modes

The syllabus mentions publish–subscribe modes. Pub/sub systems differ in how a subscriber chooses messages and how messages are delivered:

MQTT itself filters by topic only. Content-based filtering is usually added by rules engines in brokers and cloud platforms.

## MQTT-SN

MQTT needs TCP, which is too heavy for the smallest sensor networks. **MQTT-SN** (MQTT for Sensor Networks) runs over UDP or other non-TCP links such as Zigbee. It replaces long topic names with short numeric topic IDs to save bytes. A gateway translates MQTT-SN to normal MQTT.

<Callout kind="example" title="Smart building monitoring">
A college building has 200 sensors publishing to topics like `block-a/floor-2/room-204/temperature`. The facilities dashboard subscribes to `block-a/#`, and an alarm panel subscribes to `+/+/+/smoke`. Adding a new energy app needs no change to any sensor: it just subscribes.
</Callout>

## Advantages and limitations

**Advantages**

- Very small headers and low power use.
- One message can reach many subscribers; senders and receivers are independent.
- Three QoS levels let each message choose its reliability.
- Retained messages, Last Will and persistent sessions handle unreliable networks.
- Supported by every major IoT cloud platform.

**Limitations**

- Needs a broker, which is a central point that must stay up.
- Runs over TCP, which is heavy for the smallest devices (MQTT-SN helps).
- Topics carry no fixed meaning; teams must agree on naming.
- Security (TLS, passwords) must be switched on; it is not automatic.
